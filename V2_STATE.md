## Architectural decisions

- Do not repair the existing WPF/client architecture.
- The Windows/WPF client is retired.
- The new desktop client is C++ with Qt 6, Qt Quick/QML, KDE Frameworks 6 and Kirigami.
- Breeze/KDE desktop styling supersedes the old Fluent-theme requirement.
- KI18n is the localization path; KConfig is the local client-settings path.
- Reuse business rules, domain knowledge, terminology and useful workflow ideas from the legacy code; do not mechanically port implementation structure.
- Build the new server/API as a small, explicit architecture rather than generated CRUD modules.
- Server target: .NET 10 LTS.
- Persistence target: LINQ to DB for typed SQL/query composition, FluentMigrator for migrations.
- Target databases: SQLite, PostgreSQL, SQL Server, MySQL/MariaDB.
- New v2 entity IDs use UUIDv7 generated by the server. The initial SQL representation is the canonical 36-character UUID string for provider portability.
- The server must support daemon/service hosting and CLI administration.
- Configuration is external and portable; YAML is the intended human-facing format.
- Preserve UTC at persistence/API boundaries and localize only at the UI boundary.
- Avoid DTO-specific mapping frameworks when direct typed projections/commands are sufficient.
- Client accesses clinical data only through the API; never direct SQL.

## Corrected scheduling truth

This supersedes the earlier one-appointment-kind -> one-encounter-kind assumption.

- Appointment is planning truth.
- `AppointmentType` is immutable after creation.
- Appointment scheduled time and duration are operational data and may be changed while status is `Scheduled` **or `Arrived`**.
- Arrival therefore does not freeze the appointment position; this supports delays such as waiting after drinking water or a patient running late.
- Encounter is clinical reality and is not constrained to match AppointmentType.
- Walk-ins are first-class and have no appointment.
- Appointment-to-Encounter remains a one-to-one link for the clinical session that resolved that appointment.

## Corrected encounter model

`Encounter` is a clinical session/container, not a mutually-exclusive kind.

Common state lives only on Encounter:

- EncounterId
- PatientId
- optional AppointmentId
- start/end
- lifecycle status
- `RequiresExclusiveSlot`
- urgency
- notes

Clinical components are separate one-to-one extension rows keyed by the same EncounterId. Different component types may coexist on the same encounter:

- Visit
- Endoscopy
- ClinicalExam
- Prescription
- InfaiTest

Examples explicitly supported by tests/design:

- scheduled Endoscopy -> one Encounter containing Endoscopy + ClinicalExam + Prescription;
- walk-in -> one Encounter containing Rectoscopy/Endoscopy + ClinicalExam (HEINE workflow);
- INFAI-only encounter alongside an exclusive clinical encounter.

A component type occurs at most once per Encounter in the initial model. If repeated same-type components become a real requirement, that component gets child identity rather than turning Encounter back into a generic bag.

The previous `EncounterKind` column/property is removed.

## Exclusive clinical slot

The practice-wide active-slot rule is operational, not a clinical type.

- INFAI-only plans do not require the exclusive slot.
- Any Encounter containing at least one non-INFAI component requires the exclusive slot.
- A composite Encounter claims one slot regardless of how many components it contains.
- The rule is enforced transactionally through singleton `practice_state.active_encounter_id`.
